# Backend

## Foundation

The Express modular monolith exposes REST endpoints under `/api/v1`. `src/app.js` composes middleware and routes. `src/server.js` loads configuration and owns the HTTP and MongoDB lifecycles. Mongoose manages a single connection and monitors it for disconnects and reconnections. The server exposes liveness while MongoDB connects and exits on initial connection failure. On shutdown it gives HTTP connections up to five seconds to drain, closes remaining sockets, then closes MongoDB. Feature modules and schemas are scheduled for their respective phases.

## Environment

Create root `.env` from `.env.example` if needed. Process values take precedence over the root file. Supply the Atlas URI with `/fdfs` in its path and preserve its connection options. Allow the app host in Atlas network access and give the database user permissions to create application indexes and read and write application records. Startup requires a named database and `JWT_ACCESS_SECRET`. Readiness includes authentication, submission, media, audit, Talent, film, podcast and live index creation. Use a replica set for transactional operations. Keep actual environment files outside Git.

Set `APP_WEB_URL` to the exact frontend origin and include it in `CORS_ORIGINS`. Production requires HTTPS. Generate a signing key locally. This PowerShell command sets a development key for the current shell without displaying it. Use a persistent, securely managed random key for a shared environment.

```powershell
$env:JWT_ACCESS_SECRET = node -p "require('node:crypto').randomBytes(48).toString('hex')"
```

SMTP uses `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASS` and `EMAIL_FROM`. Configure both credentials if authentication is required. Transport uses implicit TLS when `SMTP_SECURE=true` and requires STARTTLS otherwise. With SMTP entirely unconfigured the API starts, accounts stay unverified until email verification succeeds, and email requests return a generic acceptance response. Partial SMTP configuration fails startup. Email sends run asynchronously without logging addresses, credentials or links.

Cloudinary uses server-only `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY` and `CLOUDINARY_API_SECRET`. The API starts without Cloudinary. Image writes return `MEDIA_UNAVAILABLE` when configuration is incomplete.

## API conventions

- `GET /api/v1/health` returns 200 when the application can serve HTTP. `GET /api/v1/ready` returns 200 when the MongoDB driver reports a connection and 503 with `DEPENDENCY_UNAVAILABLE` during database unavailability. Both responses use `Cache-Control: no-store`.
- Success uses `{ success: true, message, data, pagination? }`. Errors use `{ success: false, message, error: { code, details? } }`. Validation returns 400 with field paths and validation codes. Clients should branch on HTTP status and machine-readable error codes.
- For future list endpoints, use `page` (default 1) and `limit` (default 20, maximum 100). Where requested by the endpoint, use pagination metadata with `page`, `limit`, `total` and `totalPages`. Define an endpoint-specific page/window cap before calculating offsets.
- Plan endpoint-specific allowlists for filters and sort fields. Use `sort=field` for ascending and `sort=-field` for descending, with a unique tie-breaker. Validate query values before mapping them to database operators.
- Keep status codes and payloads consistent across clients. Use 401 for missing or invalid authentication and 403 for restricted accounts or insufficient permissions.

## Security and operations

Helmet applies security headers. CORS permits configured browser origins and accepts requests without an Origin for native and server clients. The API limits JSON bodies to 100 KiB and applies a per-IP, in-memory quota to versioned routes excluding probes. Before deploying behind a proxy or across replicas, review trusted proxy hops and shared rate-limit storage.

The server echoes a valid UUID supplied as `X-Request-Id` or generates one. Pino logs request IDs, method, status, completion and duration. Logs omit headers, bodies, URLs and raw database errors, with redaction for common sensitive fields. Internal errors receive generic responses. Build indexes through a controlled deployment step when feature schemas are introduced.

## Authentication and authorization

The private account model stores normalized email under a unique index, a bcrypt hash, viewer/creator/organizer/admin roles, verification and lifecycle status, profile metadata and preferences. Registration assigns viewer. Creator and organizer roles require administrator approval. Account updates accept full name, biography and email-update preference. Talent Profiles remain a separate model. A suspended or deleted account cannot participate. Unverified accounts can sign in, manage their own account and sessions, and request email verification. Future submissions, reviews and community routes must require verified email and the applicable current role or owner.

| Routes under `/api/v1`                                                                                     | Contract                                                                                                                                                                                    |
| ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /auth/register`, `/auth/resend-verification`, `/auth/forgot-password`                                | Generic 202 responses. Signup accepts `fullName`, `email` and `password`. Email requests accept `email`.                                                                                    |
| `POST /auth/login`, `/auth/refresh`, `/auth/logout`                                                        | Trusted browser origin and `X-FDFS-CSRF: 1`. Login accepts email and password. Login and refresh return `accessToken` and `sessionId`; the refresh credential stays in the HttpOnly cookie. |
| `POST /auth/verify-email`, `/auth/reset-password`                                                          | Accept `token` and `password`. Verification checks the existing password to prevent accepting a signup created by someone else. Reset sets the replacement password.                        |
| `GET /auth/me`, `GET/PATCH /users/me`                                                                      | Bearer-authenticated private account read and allowlisted updates.                                                                                                                          |
| `POST /auth/change-password`, `/auth/logout-all`, `GET /auth/sessions`, `DELETE /auth/sessions/:sessionId` | Bearer-authenticated password or session management. Password change takes `currentPassword` and `password`.                                                                                |

Access JWTs use HS256, a configured issuer and audience, and a 900-second default lifetime. Every protected request checks current account status, roles and session state. Refresh credentials contain a random secret. MongoDB stores its digest and atomically rotates the current digest into the used history. One concurrent request succeeds; overlap receives 409 without a cookie update. Known reuse after five seconds revokes the session. Sessions expire after 30 days by default, or sooner when revoked. TTL removes expired records. Password resets, password changes and logout-all invalidate earlier sessions through the account version. Passwords require at least 12 characters and at most 72 UTF-8 bytes for bcrypt. Auth rate limits are per IP and process, with a stored per-account resend cooldown.

The refresh cookie is host-only, HttpOnly, SameSite=Lax and scoped to `/api/v1/auth`, with Secure in production. Deploy the web app and API on the same site. Verification and recovery use one-time hashed tokens with 24-hour and 30-minute lifetimes. Links use the configured frontend origin and put tokens in the URL fragment.

Bootstrap the first administrator locally with an existing active, verified account. The confirmation must repeat the target email. The database enforces a one-time bootstrap and invalidates the promoted account's former sessions.

```bash
npm run auth:bootstrap-admin -w @fdfs/backend -- --email <email> --confirm <email>
```

## Logical MongoDB architecture

Use ObjectId references internally and immutable, unique `publicId` values in the API. Give routable content lowercase hyphenated slugs with unique indexes per collection or parent scope. Preserve old URLs through explicit redirects when changing a published slug. Store timestamps as BSON dates in UTC and serialize as ISO 8601. Publish public content through explicit draft, scheduled, published and archived states. Apply public visibility at the query layer and store moderation state separately.

Proposed collections and indexes follow. Unique keys are marked explicitly.

| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Users and sessions                       | User identity and roles. Unique normalized email and public ID. Sessions reference users, use hashed credentials with a unique digest, and index user plus a TTL on expiry. Enforce expiry and revocation on lookup.                                                     |
| Personalities and achievements           | Shared profiles for creators, cast, crew and guests. Unique public profile slug. Achievements reference personalities and index personality and achievement date.                                                                                                        |

Participants reference episodes and personalities with a unique episode/personality/role key and a reverse personality index.                                    |
| Live events and organizers               | Events reference a user in the organizer role or the administrator who created the event. Index publication, broadcast and start time, plus organizer and start time. Track moderation, publication and broadcast independently.                                         |
| Mainstream movies                        | Catalog metadata with unique provider and external ID pairs where present, plus title/release year and publication indexes.                                                                                                                                              |

Check references and allowed target types in services. Use transactions where writes across collections must succeed together. Archive public content and keep attribution and moderation history when references must survive removal. Revoke user sessions on deletion, anonymize retained contributions according to policy, and clean up private user records. Unlink or clean up dependent records before permanent deletion. Use UTC timestamps, typed public IDs in payloads and consistent pagination so both clients can follow the same links and rules.

## Shared media

Image writes accept raw still JPEG, PNG or WebP up to 5 MiB. The server checks signatures, decodes the source with a pixel limit, rejects mismatched and animated inputs, strips metadata and re-encodes to WebP within a 2400px box. A per-IP upload quota applies after authentication and authorization. Cloudinary receives signed server uploads from those normalized bytes. [Cloudinary Node upload reference](https://cloudinary.com/documentation/node_image_and_video_upload)

`MediaAsset` tracks the public application ID, Cloudinary public and asset IDs, owner, purpose, dimensions, byte size, secure delivery URL, references and lifecycle status. Responses provide size-limited variants as well as the original normalized image. Verified active users can read and replace their own avatar via `GET/PUT /api/v1/users/me/image`. Library replacements create a new asset ID. Live references block deletion or replacement. Future content modules should use the reference helpers in the same transaction as their feature records. Run `npm run media:cleanup -w @fdfs/backend` to retry pending deletes and clean staged uploads older than one hour, in batches of 100 pending deletions.

The video source contract stores provider, provider video ID, canonical source URL, playback type, availability, and optional duration and thumbnail dimensions. YouTube supports on-demand, scheduled live, active live and replays through one adapter. Availability starts unknown unless established by the feature. The contract accepts validated YouTube watch, short-link, embed and live URLs.

## Audit retention

Audit entries store the actor, action, target, safe change summary, request ID, timestamp and success outcome for committed administrative mutations. The API exposes paginated reads to administrators. Application-level updates and deletes are unavailable. Keep indexes for time, target, actor and action. Set a production retention policy based on operational and privacy requirements before enabling automatic expiry.

## Talent Profiles

`Personality` is the shared public identity for cast, crew, filmmakers and guests. It has an immutable public UUID and unique slug, public profile fields, a controlled multi-role taxonomy and draft, published and archived states. Achievements reference the personality ObjectId and can include optional supporting URLs. Submitted achievements and links are profile claims. Match queries use normalized name prefixes, including alternative names and later words. Indexes cover public slug, associated account, published listing, professions and name search. Matching names can identify distinct records.

| Routes under `/api/v1`              | Contract                                                                                                                                  |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /talent`                       | Published directory using `q`, `profession`, `sort`, `page` and `limit`. Sort supports `name`, `-name` and `newest`.                      |
| `GET /talent/:slug`                 | Published public fields, achievements and sized image variants. Returns 404 for unpublished, archived and missing profiles.               |
| `GET/POST /admin/talent`            | Search all profiles, optionally filter by `status`, and create drafts with a generated or explicitly chosen slug.                         |
| `GET/PATCH /admin/talent/:id`       | Read private management fields and edit profile content with the last-read `revision`.                                                    |
| `POST /admin/talent/:id/status`     | With a matching revision, publish a draft, unpublish to draft, or archive a profile. Archival retains the record and media relationships. |
| `PUT /admin/talent/:id/association` | Approve an active verified user UUID with a matching revision, or send `null` to remove the association.                                  |

Administrator mutations require the current verified administrator role and are audited. An approved account association is private, grants zero permissions and is unique per account. Public responses omit account associations, revisions and internal ownership. Profile and achievement writes commit with media references and the audit entry.

Owners use the existing submissions API with `category: "talent"` and `proposal: { targetId?, profile }`. A target must be a published profile. Only the submitter can edit draft or rejected proposals. An exact open creation proposal per owner or a second open correction by the same owner to the same target returns a conflict. Corrections record a target revision and require review against that same revision at publication. Approve or reject through the shared moderation route, then publish through the same submission publishing endpoint. Publication applies validated profile content and atomically records the resulting public resource and both audit entries. Older text-only submissions need structured details to publish.

Verified submitters can upload owned media via `POST /submissions/talent-images` using the same raw bytes, validation and rate limit as the media library. Proposal asset IDs must belong to the submitter. Administrator editors can attach library or talent assets. Proposals and profiles hold explicit references. Publishing transfers references to the personality, and archiving a proposal releases proposal references. An image with an active reference is protected from deletion and replacement.

Filmography reads film credits joined to released films. Podcast appearances join episode participants to released episodes of a published show. Personality records hold the stable profile identity, while related titles and publication visibility come from the owning content modules.

Submission requires rights confirmation across the film, videos and uploaded images, a valid main video URL and a detailed description. Private rights notes, the attesting account and time remain protected. Approved proposals publish through the shared endpoint with `release: { playbackChecked: true, releaseAt?, announce? }`. Creator corrections retain the stable film record and use its original inspected revision to prevent stale writes. Originals require an administrator and an authorized production company. Administrators unpublish before direct edits. Changes to independent film video sources or rights go through creator review.

Announcements can include the distinct approved trailer. Main video metadata and behind-the-scenes videos become available at the UTC release time. Drafts and archives remain private. Film media use existing Cloudinary assets with shared validation, responsive variants and transactional reference transfers from the proposal to the published film. Archive preserves film, credit and media relationships. Public credit links resolve only published profiles, and public filmography includes released films only. Publication, corrections, direct edits, unpublication and archival are audited.

Publication and broadcast are explicit. The scheduled time can put a page into its waiting state. An operator issues the transition to live when the real broadcast is ready, and ends the event when the transmission finishes. FDFS records actual transition times using the server clock. YouTube controls input availability, embedding and playback. Set up OBS and the channel in YouTube Studio, confirm distribution rights, and use an embeddable live or replay URL. Keep stream keys in the broadcaster's external tools. [YouTube encoder setup](https://support.google.com/youtube/answer/2907883) · [YouTube IFrame Player API](https://developers.google.com/youtube/iframe_api_reference)

Socket.IO attaches to the Express HTTP server at `/socket.io/` and uses the same origin allowlist as REST. Native clients may omit Origin. Guests may join published event rooms. For protected operations send a current bearer access token as handshake `auth.token`. `event:join` and `event:leave` take `{ slug }`. `chat:send` takes `{ slug, clientId, text }`. Acknowledgments return `{ ok: true, data }` or `{ ok: false, code, message }`. Sockets recheck current sessions, account status and verification on each send. Refresh an expired JWT through the client session flow and reconnect with the new token.

Successful writes emit `chat:message` with `{ slug, id, text, name, createdAt }`, `chat:removed` with `{ slug, id }`, or `live:state` with `{ slug }`. Re-fetch public state and history on reconnect or state invalidation. MongoDB stores messages and reports separately and uniquely indexes each event, author and client message ID. Text has a 400-character limit, with limits per connection and per event participant. Guests can read enabled chat on shared events. Sending requires a live broadcast. Slow mode and mute expiry are enforced server-side. Moderation actions and report resolutions are audited. Room updates stay on one server instance. Horizontal scaling would require a shared Socket.IO adapter, shared rate limits where applicable, and sticky routing for polling. [Socket.IO deployment guidance](https://socket.io/docs/v4/using-multiple-nodes/)

The database-backed SMTP worker scans every `LIVE_REMINDER_INTERVAL_MS` (default 60000). It schedules eligible subscriptions `LIVE_REMINDER_LEAD_MINUTES` (default 15) before start. Launch the backend continuously with a working SMTP sender and capacity for the expected recipients. A unique event/user record, schedule versions and guarded leases prevent repeated sends for the same schedule. Rescheduling can create a new delivery generation. Cancellation, unsubscription, loss of visibility, disabled reminders and expired eligibility prevent pending sends. Definite transient SMTP rejection gets up to three total attempts per generation. A lease abandoned before SMTP can be reclaimed on restart. If SMTP may have accepted a message before the worker could record the result, the job becomes `uncertain` and is held. Changes made after SMTP handoff may arrive too late to stop delivery.

## Centralized administration

The shared staff policy applies to the web administration navigation and the API. Administrators retain content, moderation, regular user management, media and site settings. A Super Administrator can also assign staff roles and module scopes. Content Managers can publish and review submissions in assigned modules and use the library. Moderators can review submissions and moderate reports, podcast comments and live chat. Publishing a submission also requires the corresponding content scope. Support Agents have access to the scoped support workspace. Role changes revoke prior sessions through the account version, which protected REST operations and authenticated socket sends check.

From a local interactive terminal in the repository root, confirm the configured MongoDB URI selects the intended `fdfs` database. Run the one-time owner bootstrap and enter a new unique password twice at the hidden prompts.

```bash
npm run auth:bootstrap-super -w @fdfs/backend -- --email admin@fdfs.one --confirm admin@fdfs.one
```

The command requires a terminal. It commits the bcrypt hash, active and verified state, role assignment and safe audit entry together. Trusted bootstrap verification does not establish ownership of the external mailbox. Existing staff remain in place. A rerun for the active bootstrap account returns its existing status. For an existing active, verified administrator, confirm account ownership first and append `--elevate-existing`, then type the address again at the prompt. Elevation retains the existing password and revokes older login sessions. Last-active-owner protections still apply.

Use `PATCH /api/v1/admin/users/:id/staff` with a role, enabled flag and reason. Enabling Content Manager requires a nonempty module list. `GET /api/v1/admin/overview` returns permission-scoped account, release, Talent, Live, submission and report counts plus recent audit entries for authorized accounts. Audit filters accept `actor`, `action`, `resource`, `target`, `from`, `to` and `outcome`. Submission correction requests record a reason and return the item to its submitter for revision. The consolidated live moderation lists are under `/admin/moderation/live-events` and `/admin/moderation/live-reports`. Existing scoped chat routes handle moderation and emit safe invalidations after restoration.

Direct independent-film drafts use `POST /api/v1/admin/cinema` with `classification: "independent"`. Originals keep `POST /api/v1/admin/films` and `classification: "original"`. Both use the same model, revision, rights checks, status service and protected previews. With `keepPublished: true`, an authorized staff member can edit directly created film metadata or podcast episode metadata while preserving release and authorized sources. Changes to the source or distribution rights require unpublication. Creator-submitted films retain their existing correction rules. Live events allow an optional UTC `publicationAt` on publish. Visibility follows that time while the broadcast continues to require an explicit start. The optional planned replay stays private until separately approved and published after the event ends.

The Cloudinary library supports category, text, and usage filters. Media metadata includes alternative text, dimensions, bytes, upload attribution and protected usage references. The selector uses shared library assets. There is no public library listing. Support screenshots use their own private MongoDB collection and protected delivery route.

### Analytics, support and operations

Presence shares the live chat Socket.IO server with separate pulse and subscription handlers. The bounded in-memory store accepts up to 10,000 recent connections and expires them using server time. The default heartbeat is 30 seconds, expiry is 90 seconds and administrator broadcast interval is five seconds. A browser pulse marks recent activity when the page is visible and has seen activity within five minutes. Active playback on an eligible live event can count while hidden. Authenticated accounts deduplicate across sessions and devices. Guest browsers deduplicate through a random first-party ID that rotates daily. An identified guest tab on the same browser is suppressed when an authenticated tab is eligible for counting. Authenticated pulses and administrator streams recheck session validity. Disconnect and staleness remove entries. Single-instance counts rebuild from browser pulses after restart. Shared presence storage and a Socket.IO adapter are needed for cross-instance counts.

`GET /api/v1/admin/activity` exposes totals and grouped presence to authorized administrators. The authorized `ops:subscribe` stream emits an aggregate snapshot. Login sessions come from active, unexpired, unrevoked, version-matching records. Registered accounts and daily registrations come from user records. Event-page presence measures activity on FDFS event pages. It provides no official YouTube audience measurement.

`POST /api/v1/analytics/events` accepts an idempotency UUID, page or observed playback-start kind, allowlisted module and device category, and an optional validated public content slug. The browser sends these events after opt-in. MongoDB atomically inserts the raw event and updates the daily dimensions and keyed account-per-day records. Every event timestamp is assigned at ingestion in UTC. The initial reporting timezone is Asia/Kolkata. Timezone changes start a separate traffic series. The reporting API supports 1, 7, 30 and 90 days plus custom ranges up to 90 days. Trends show missing traffic data when no events were collected. Distinct aggregates deduplicate keyed account IDs across the selected calendar dates. Registration and support counts use the original records. Page and playback counts are first-party, client-observed data and can be influenced by client behavior.

`ANALYTICS_ENABLED` and Website Settings control collection. Defaults are 30 days for raw events and 365 days for aggregates and per-account/day pseudonyms. TTL indexes remove expired records. The API excludes expired aggregates before MongoDB cleanup runs. Analytics stores no IPs, full URLs, guest browser IDs, private input or raw account IDs. Account deletion procedures can derive the account's analytics pseudonym and remove its daily markers before deleting the account. Aggregate counts have no per-account link. Removing markers does not alter earlier aggregate event counts. Retention changes apply to new writes. Keep the signing secret stable over a reporting window to preserve deduplication, and rotate it if compromised.

Signed-in support routes under `/api/v1/support/tickets` enforce ownership. Staff routes under `/api/v1/admin/support` require explicit Support permission. Ticket lists, conversation and scoped audit history paginate independently. Staff assignments, priority, status and protected attachment reads record immutable audit events. Owner replies to tickets awaiting a response advance them to in progress. Owners may reopen resolved or closed tickets within 30 days. Staff notes never appear in owner responses or notices.

Guest initiation accepts a new ticket draft or the email and reference of an existing guest ticket. It responds generically and applies an IP limit and a maximum of three challenges per address per UTC hour. Verification links expire after 30 minutes and redeem once. The resulting bearer credential uses the `Guest` authorization scheme, expires after 24 hours and applies to one ticket. The challenge and access documents store token hashes. Deliver verification links only using the trusted frontend origin and keep tokens in the URL fragment. The browser removes the fragment after reading it. Recover guest access through a new verified link.

Support screenshots use private MongoDB binary storage and never enter the public media library. Only authorized ticket users and staff can fetch them. Upload accepts validated PNG, JPEG and WebP, normalizes to WebP without metadata, and permits three current images of at most 2 MiB apiece. Use `SUPPORT_ATTACHMENTS=false` to stop new uploads. `SUPPORT_ATTACHMENT_DAYS` defaults to 90 and accepts 1 to 365 days. The API rejects expired reads before database TTL cleanup. Configure database encryption and apply the same retention rules to backup copies. Ticket and conversation text remain until removed by an authorized retention process.

The support email worker scans the durable MongoDB queue every 15 seconds. Ticket writes and notification jobs commit together. It separates claimed, sending, accepted, retry, failed and uncertain outcomes. Explicit transient SMTP responses may be retried up to `SUPPORT_EMAIL_ATTEMPTS`. A worker interrupted after a send begins marks the abandoned result uncertain, avoiding an automatic duplicate. `SUPPORT_STAFF_EMAIL` enables assigned-staff follow-up messages. SMTP acceptance confirms provider handoff. Inbox delivery requires recipient-side evidence. Future promotional messaging requires a separate consent, unsubscribe and delivery design.

Account notices under `/api/v1/notifications` expose listing, unread count and owned read operations. The Socket.IO notice signal prompts authenticated clients to refetch. Announcement drafts, previews, publication and archival are managed under `/api/v1/admin/announcements`. Public and checked account announcement routes use allowlisted audiences, start and end times and plain text. Privileged writes use revisions and the shared audit log.

`GET /api/v1/admin/system-health` shows application version, database readiness, observed socket and presence state, last analytics aggregation, worker results and safe recent email and Cloudinary outcomes. Missing evidence appears as not checked. During a database outage, use the independent health and readiness endpoints to diagnose the API and database. No backup telemetry is configured. Production infrastructure monitoring remains Phase 8.

### Movie catalogue and Reviews

`GET /api/v1/movies` accepts `q`, `genre`, `language`, `year`, `sort`, `page` and `limit`. Sort values are `release`, `published`, `title`, `rating` and `popular`. Popularity uses eligible rating volume. Ranking requires three eligible votes and applies a five-vote, three-star prior. Unrated titles display a null average and zero counts. Slug detail and credits are at `/movies/:slug` and `/movies/:slug/credits`. Public projections expose optional source metadata and external ratings separately. The Movie model uniquely indexes slug and provider identity. Credits reference existing Talent records. Talent profiles derive published movie appearances alongside existing filmography and podcast appearances.

Scoped staff manage entries under `/api/v1/admin/movies`, with revisioned PATCH and `POST /:id/status`. Preview reads the protected draft. Artwork uses the media library and transactional reference protection. Trailer URLs use the existing YouTube validator and require a rights attestation to publish. Public records contain no full-movie streaming source.

The provider adapter boundary supports search, preview, confirmed draft import and revisioned refresh. Production returns unavailable. Isolated tests inject a provider. The service validates normalized responses, uses a bounded cache and passes a five-second abort signal. Drafts retain unmatched people and image references for review. Refresh fills missing editable fields and preserves staff changes and trailer authorization. A future TMDB adapter requires authorized data and image use, approved attribution, backend-only `TMDB_READ_ACCESS_TOKEN` and fixed trusted endpoints. Commercial data and image use has separate licensing terms. [TMDB API licensing and attribution](https://developer.themoviedb.org/docs/faq)

`/api/v1/ratings/:type/:slug` serves public totals, verified-account PUT and DELETE, and the signed-in rating at `/mine`. Types are `movie`, `cinema` and `original`. Ratings use integer half-star units and target the Movie or existing Film by ObjectId. A transaction serializes publication and engagement and keeps the rating row, count, sum and distribution consistent. Unique indexes enforce one rating and one active primary review per account and target.

`/api/v1/reviews/:type/:slug` supports GET and POST, while `/mine` and `/:id` serve the account review and public detail. The author can PATCH or DELETE by ID. Listings support recent, liked, trending and exact half-star filters. `/api/v1/reviews/trending` uses visible targets and a 14-day window. A recent like scores one, a recent published comment scores two, and a newly published review scores one. Creation time and ID break ties. Likes use PUT and DELETE at `/:id/like`. Comments use GET and POST at `/:id/comments` and author PATCH and DELETE at `/:id/comments/:comment`. Append `/report` to either content URL. Review text is plain text. Public author projections expose a display name and public ID for active accounts, and a generic label for other accounts.

Moderators use `/api/v1/admin/review-moderation/reports` to hide, restore or dismiss with a reason. Text moderation leaves the independent rating intact. A reasoned, audited rating exclusion or restoration changes eligibility while preserving its submitted value. Unique-account controls and limits contain basic duplicate activity. Staff still investigate coordinated abuse. Owned notifications cover comments and moderation. Comment alerts are deduplicated per author and review per UTC day. Existing analytics consent and retention apply to published movie and review details and authorized movie trailers.

The Phase 5.2 read APIs add `GET /api/v1/reviews/feed` with `type`, `sort`, `rating` and pagination. Feed summaries omit spoiler titles and bodies. Title-scoped lists accept `summary=true`. `GET /api/v1/reviews/entry/:id` resolves the published target and omits marked spoiler text until `reveal=true`. The established title-scoped detail contract remains available. Signed-in clients can batch up to 24 public IDs through `GET /api/v1/reviews/likes?ids=id1,id2` to read their own like state.

`GET /api/v1/account/reviews?kind=reviews|ratings` returns a private paginated list. Targets are projected only while publicly available. Delete owned entries through `DELETE /api/v1/account/reviews/reviews/:id` or `/ratings/:id` under that account route. Removing an eligible rating updates existing totals transactionally. The public films API accepts `ratings=true` for batched rating summaries in short-film discovery.

The scoped administrator review catalogue and detail are under `/api/v1/admin/review-moderation/reviews`. Review and comment status changes require a moderation reason and reuse the report workflow's visibility service. The detail includes paginated comments and a separate audit list. Report resolution stays available in the queue. Review comment notifications lead to review permalinks, and moderation notifications lead to the owner's history.

The account system has a deleted status, and public views mask missing or inactive authors. Full cross-module account erasure and retention handling is mandatory Phase 7.1 work. The process must reconcile rating totals and address review interactions, audit obligations, pseudonyms, media and support records. Phase 5.2 retains existing account references and adds owner-scoped deletion of review or rating entries.
